# Single-pass RAG vs agentic RAG on Qdrant: benchmark results

Run date: 2026-10-28. All numbers below come from `runs/main/report.md` and `runs/main/summary.json`, produced by `scripts/analyze.py`.

**Objective:** find where iterative retrieval measurably helps and where it costs. The goal was not to show that agentic RAG wins.

## 1. Setup

### Data and index
- **Corpus:** 1,000,000 chunks from seven Stack Exchange technical sites: Server Fault, Unix & Linux, Software Engineering, DBA, Security, Network Engineering and DevOps (CC BY-SA 4.0 dumps from archive.org).
  - Answers are kept if accepted or scored at least 1.
  - Chunks are at most 500 characters, each prefixed with its question title.
- **Qdrant:** Qdrant Cloud v1.19.1, 1 vCPU, about 1.8 GB RAM, collection `rag_bench_se_1m`.
  - HNSW m=16, ef_construct=100, query hnsw_ef=128.
  - Original vectors on disk; int8 scalar quantization in RAM with rescoring.
- **Embeddings:** `sentence-transformers/all-MiniLM-L6-v2` (384-d) through Qdrant Cloud Inference, for both indexing and queries.

### Model
Claude Sonnet 5.5 for both pipelines, run as Claude Code sub-agents with 8 questions per sub-agent.

### Pipelines
Both pipelines get the same questions and the same answer rule: answer only from retrieved text and cite chunk ids, or record NOT_FOUND.

- **Single-pass:** one dense search on the raw question text, the top 10 chunks shown once, then one answer.
- **Agentic:** the model can call:
  - `search(query, page)`: 10 results per page, up to 50 deep.
  - `open(post)`: the full answer a chunk came from.

  The budget is 6 search/open calls per question. A 7th call closes the run as "budget", which is scored as NOT_FOUND.

### Questions
200 questions, 50 per type. Generated by Sonnet sub-agents from the corpus, then checked by independent Opus verifiers with fresh context. The set was frozen and hashed before any run.

| Type | What it tests |
|---|---|
| Straightforward | The answer sits in one chunk; the question uses similar wording. |
| Semantic | Same kind of fact, but paraphrased to avoid the source's distinctive terms. |
| Multi-document | Needs facts from two linked threads; neither thread alone is enough. |
| Unanswerable | Written from threads removed from the index. Verifiers confirmed absence with at least 3 dense (Qdrant) and 3 keyword (BM25) searches each. |

### Trials, grading and metrics
- **Trials:** 3 per pipeline, giving 2 x 200 x 3 = 1,200 runs. Every run completed: no missing or duplicate runs and no tool-server errors.
- **Grading:** Opus judges, blind to pipeline and trial, labelled each run against the reference answer and evidence as correct, partial, incorrect or not_found. They also marked whether the cited chunks support the answer.
  - A 20% sample (240 runs) got a second independent judge.
- **Scoring rules (fixed before the runs):**
  - Answerable questions: correct; **unsupported** = partial or incorrect; **missed** = NOT_FOUND or budget exhausted.
  - Unanswerable questions: NOT_FOUND = **correct refusal**; any answer = unsupported.
  - Paired tests use the trial-majority outcome per question, with an exact McNemar test.

## 2. Headline results

| Question type | Single-pass correct | Agentic correct | Paired test (trial-majority, 50 questions) |
|---|---|---|---|
| Straightforward | **98.0%** | 96.7% | 49 vs 49, no difference (p=1) |
| Semantic | 47.3% | **92.0%** | 24 vs 47; agentic-only 23, single-only 0 (p=2.4e-7) |
| Multi-document | 22.7% | **69.3%** | 11 vs 37; agentic-only 28, single-only 2 (p=8.7e-7) |
| Unanswerable (correct refusal) | **100.0%** | 98.0% | 50 vs 50 (p=1) |
| **All answerable (150)** | **56.0%** | **86.0%** | 84 vs 133; agentic-only 51, single-only 2 (p=3.2e-13) |

The correct rate varied little between trials: at most 2 points for single-pass and 4 for agentic on any type.

## 3. Where iterative retrieval helps

1. **Paraphrased questions (semantic): +45 points.**
   - Single-pass top 10 contained none of the reference evidence in 56% of semantic runs.
   - Agentic retrieval cut that to 13% by rephrasing the query.
   - Whenever single-pass did retrieve all the evidence, it was correct 48 of 48 times. So its failures here are retrieval failures, not reading failures.
2. **Multi-document questions: +47 points.** One query rarely surfaces both threads.
   - Single-pass got all evidence in 14% of multi runs and only part of it in 54%. With part of the evidence it often answered half the question (44 partial runs).
   - Agentic got all evidence in 38% of runs, using 3.2 calls on average.
3. **Single-pass misses: agentic recovered 91 of 135.** These are run pairs (same question, same trial) where the single-pass top 10 held none of the evidence:
   - Single-pass was correct in 15 of these pairs, agentic in 106.
   - Agentic fixed 91 and lost none.
4. **Reading wider when the evidence was already there: 56 fixed, 12 lost.** These are pairs where the single-pass top 10 held at least one evidence chunk:
   - Single-pass was correct in 237 of 315, agentic in 281.
   - Agentic fixed 56, mostly by opening the full post or finding the second thread, and lost 12.

## 4. Where it does not help, or costs

1. **Straightforward questions: no accuracy gain, same cost.**
   - Agentic mostly stopped after one search (1.12 calls on average) and matched single-pass latency.
   - It scored 1.3 points lower (5 partial runs vs 3); the paired test shows no difference.
2. **Unanswerable questions: the most expensive case, with a small accuracy loss.**
   - Agentic spent the full 6-call budget on 143 of 150 unanswerable runs: 5.9 calls and about 5,500 retrieved tokens per question.
   - Its median latency was 15.2 s vs 2.9 s for single-pass.
   - It still answered 3 of 150 unanswerable runs with loosely related material. Single-pass refused all 150.
   - Proving absence is where the agent burns its budget.
3. **Less repeatable.** The same outcome in all 3 trials held for 91% of questions with single-pass and 84% with agentic.
4. **Budget mistakes.** 10 agentic runs were closed by the budget cap. Several sub-agents reported reaching the cap with an answer in hand because they miscounted their calls.

### Overall trade
Across the 150 answerable questions, agentic added:
- 30 points of accuracy;
- about 1 extra retrieval call;
- about 820 extra retrieved tokens per question.

On unanswerable questions it added 4.9 calls and 4,500 tokens per question, for 2 points less accuracy.

Qdrant itself was under 5% of per-question latency in both pipelines. Model rounds dominate.

### How the numbers were measured
- **Retrieved context tokens** (exact, about 4 characters per token): the text each run put in front of the model, taken from the server event log. This is the clean per-question token measure.
- **Sub-agent tokens:** each batch sub-agent's total divided by its 8 questions. They are inflated by Claude Code's own prompt and by context carried across the batch. The ratio between pipelines (2.3x) is more meaningful than the absolute numbers.
- **Latency:** sub-agents often worked on several questions at once, so a run's raw wall clock overlaps other questions' work. Per-question latency was therefore rebuilt from transcript timestamps (`scripts/latency.py`):
  - It is model time plus exact Qdrant time, with each multi-question model turn split evenly between the questions it served.
  - The "upper bound" row charges each question the full turn.
  - Claude Code's Bash-tool overhead (seconds per call) is excluded from both, because a production pipeline would not have it.
- **Qdrant time per query** includes Cloud Inference embedding of the query and the network round trip from a laptop.

## 6. Measurement checks

- **Judge agreement:** on the 240 double-judged runs:
  - 99.6% exact label agreement (Cohen's kappa 0.99), with a single disagreement (correct vs partial).
  - On answered items only, 99.3% (kappa 0.98).
- **Sensitivity:**
  - Dropping the one accidental "NOT_FINAL" answer (see limitations) moves agentic answerable accuracy from 86.0% to 86.2%.
  - Giving partial answers half credit moves single-pass from 56.0% to 62.6% and agentic from 86.0% to 91.0%.
  - Swapping in the second judge's labels on its sample changes the single-pass correct count by 1 (47 to 46) and the agentic count by 0.
- **Retrieval sanity:** when single-pass retrieved all the reference evidence, it was correct in 210 of 210 runs (141/141 straightforward, 48/48 semantic, 21/21 multi).

## 7. Side finding: absence is hard to establish in a large knowledge base

To build unanswerable questions, 251 candidates were written from threads that are not in the index (no linked thread indexed either).
- Verifiers dropped 168 of them. In 164 of those, the drop reason cites another indexed post that already answers the question.
- About two thirds of seemingly missing knowledge was present elsewhere in a 1M-chunk technical corpus.
- This is also why the agentic pipeline searched to its limit before refusing.

## 8. Limitations

1. **One model, run through Claude Code, 8 questions per sub-agent.**
   - Accuracy, refusals and call counts are exact. Tokens and latency are estimates, as described in section 5.
   - The single-pass agent also spent one model round issuing the context call, which a production single-pass pipeline would not need.
2. **The embedder is small (MiniLM-L6, 384-d) and dense-only.**
   - Much of the agentic gain on semantic questions compensates for weak first-stage retrieval.
   - A stronger embedder, hybrid search or reranking could narrow the gap. That was not tested.
3. **Questions are LLM-written from specific chunks.**
   - Straightforward questions track their source wording by design.
   - The generators (Sonnet) and the judges (Opus) are the same model family as the pipelines' model.
4. **Unanswerable questions are the 82 candidates (of 251) whose absence the verifiers could confirm, sampled down to 50.**
   - Real-world "not in the knowledge base" questions with near-miss content may be harder.
5. **Budget exhaustion counts as a refusal (pre-registered).**
   - On unanswerable questions this credits 7 agentic runs that never chose to stop.
6. **Harness artifacts.**
   - Answers were recorded through a shell command, so a few answers containing `$` variables lost text (judges flagged 2 or 3). This affects both pipelines.
   - One agentic run recorded "NOT_FINAL" by accident; it is kept as recorded.
7. **Deviations from the design.**
   - `open` returns one full answer post, not a whole thread.
   - Batches were randomly shuffled per trial and pipeline (seed 4242). The planned "no related questions in one batch" rule was not enforced.

## 10. Follow-up: gated pipeline (one search, escalate to the agent when retrieval looks weak)

Added after the main run (2026-10-28). Scripts: `scripts/gate_signals.py` and `scripts/gate_eval.py`. Full tables are in `runs/main/gate_report.md`.

### Method
This follows Couzon, "Predicting Weak Retrieval Without an LLM".
- The 200 single-pass searches were rerun with scores. All 200 returned exactly the top 10 the logged runs saw.
- Window: the top 10. A retrieval is weak when the window lacks the question's evidence; unanswerable questions always count as weak.
- Three cheap signals:
  - top-1 cosine (`max_score`);
  - variance of the top-10 cosines (`dense_variance`);
  - dense-vs-BM25 top-10 overlap.
- Signal choice and floor (the Youden point) come from a calibration half. Results are measured on the held-out half, averaged over 500 random 50/50 splits.
- Each gated question takes the recorded outcome of the same question and trial from the single-pass run or the agentic run. No model was rerun.

### Signal quality
`dense_variance` separated best: AUC 0.82 overall.
- Strong on straightforward questions: 0.94.
- Weak on semantic and multi-document questions: 0.72 and 0.60.

### Held-out results
| Pipeline | Escalated | Answerable correct | Unanswerable refused | Calls / q | Retrieved tokens / q | Latency p50 / p95 |
|---|---|---|---|---|---|---|
| Single pass | 0% | 56.1% | 100.0% | 1.00 | 997 | 3.1 / 6.8 s |
| Always agent | 100% | 86.1% | 97.9% | 2.96 | 2,727 | 4.9 / 20.3 s |
| **Gated (signal and floor from calibration)** | 66% | **81.3%** | 97.9% | 3.26 | 2,419 | 4.5 / 20.0 s |
| Random escalation, same rate | 66% | 75.7% | 98.6% | 2.97 | 2,148 | 3.9 / 18.9 s |
| Oracle (escalate only answerable misses) | 40% | 88.6% | 100.0% | 2.05 | 1,541 | 3.4 / 15.4 s |

### Findings
1. **The gate recovers most of the agent's accuracy gain.** It reaches 81.3% vs 56.1% for single-pass and 86.1% for always-agent. It beats random escalation at the same rate by 5.6 points, so the signal is real.
2. **It does not save cost against always-agent.**
   - It makes 3.26 calls per question vs 2.96, because each escalation pays the first search plus a full agent run. Even if the agent reused that search for free, it would be about 2.6 calls, roughly 12% fewer, for 5 points less accuracy.
   - The reason: the questions the gate keeps on one search are mostly straightforward, and on those the agent already stopped after about 1.1 searches. **The agent was already gating itself.**
3. **The expensive case is the questions with no answer.**
   - Every cheap signal sees them as weak, so the gate sent 88% of them to the agent: about 6 calls and 15 s each, for no gain.
   - A weak retrieval and a missing answer look the same from the scores.
   - This matches the ceiling stated in the source article: no cheap signal catches a missing hop, and when there is nothing to find, the win is abstaining.
4. **A perfect gate would win** (88.6% at 2.05 calls). The real gate falls short on semantic and multi-document misses (AUC 0.72 and 0.60) and cannot tell weak retrieval from absence.

### Side estimate: a smaller search budget
This is simulated from the same logs: a run that needed more calls than the cap is counted as NOT_FOUND.

| Agent budget | Answerable correct | Unanswerable refused | Calls / q | Latency p50 / p95 |
|---|---|---|---|---|
| 6 (as run) | 86.0% | 98.0% | 2.97 | 4.9 / 20.5 s |
| 4 | 82.4% | 100.0% | 2.34 | 4.9 / 13.8 s |
| 3 | 80.4% | 100.0% | 1.99 | 4.9 / 10.5 s |

- A 3-call budget matches the gate's accuracy at about 60% of its calls and half its p95 latency.
- The estimate is conservative for answerable questions: with fewer calls the agent might still have answered from what it had.
- It is optimistic for unanswerable ones: it assumes a capped agent says "not found" rather than answering from thin evidence.
- Confirming it needs a rerun with the smaller budget.
